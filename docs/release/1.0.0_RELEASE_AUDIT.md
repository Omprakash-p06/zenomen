# ZenOmen 1.0.0 — Comprehensive Release Readiness Audit

- **Date:** 2026-11-11
- **Status:** Release Audit Completed & Remediations Identified
- **Target Release:** ZenOmen 1.0.0
- **Scope:** Complete repository inspection across runtime code, build configuration, hardware safety, packaging, installation lifecycle, and CI/CD distribution.

---

## 1. Executive Summary

ZenOmen is a lightweight, cross-platform hardware control and telemetry suite for HP Victus and OMEN laptops built with Rust and Slint. The project has achieved verified core functionality on its primary hardware target: **HP Victus 15-fb0xxx (Motherboard 8A3D, BIOS F.22)**.

The objective of ZenOmen 1.0.0 is to deliver an installable, predictable, maintainable, and honest release without adding experimental or unvalidated hardware controls.

This audit evaluates the repository against 12 critical engineering criteria, documents all identified defects with root causes, classifies them by severity (P0–P3), details remediation actions taken or required, specifies regression tests, and indicates whether physical hardware validation is necessary.

---

## 2. Issue Classification Hierarchy

- **P0 (Release Blocker / Hardware Safety):** Issues capable of causing firmware instability, hardware misbehavior, EC state lockups, or safety violations. Must be completely resolved before any release tag.
- **P1 (Major Functional / Installation Problem):** Issues causing installation failures, service startup failures, broken release artifacts, or unauthorized capability claims.
- **P2 (Release Quality Improvement):** Issues affecting telemetry precision, visual asset fidelity, cross-platform code purity, or documentation completeness.
- **P3 (Deferred Feature):** Non-blocking enhancements, experimental controls, or features requiring additional hardware platforms before implementation.

## 3. Comprehensive Audit Register (12 Criteria)

### Issue AUD-01 (Hardware Safety / EC State): Board 8A3D Auto Fan Restoration & Upstream hp-wmi Differences
- **Criterion:** 1. Runtime bugs / 3. Unsupported hardware assumptions
- **Severity:** **P0**
- **Exact File & Location:**
  - `src/service/windows/hp_wmi.rs` (lines 38–72, `VICTUS_S_BOARDS`)
  - `src/service/windows/victus_s.rs` (lines 14–48, `restore_auto_mode`)
  - Linux `hp-wmi` kernel driver (`drivers/platform/x86/hp/hp-wmi.c`, function `hp_wmi_apply_fan_settings`)
- **Current Behaviour:**
  - Switching from Max Fan to Auto mode on motherboard 8A3D under low temperatures (~35–37°C) frequently produces 0 RPM telemetry.
  - In earlier documentation drafts, this was characterized as either an EC stall or an assumed "45–50°C activation threshold."
  - Furthermore, upstream Linux kernel `hp-wmi` driver executes `hp_wmi_fan_speed_set(priv)` using WMI opcode `0x2E` with data `{0, 0}` during automatic fan restoration on Victus S laptops.
  - On board 8A3D with BIOS F.22, issuing `0x2E {0,0}` causes the embedded controller (EC) to stall, preventing fans from ramping up even when temperatures escalate under load.
- **Expected Behaviour:**
  - 0 RPM at idle temperatures (~35–37°C CPU/GPU) is standard EC passive cooling behavior. It must not be labeled as a malfunction unless fans fail to ramp up under thermal load.
  - Documentation must not cite 45–50°C as a confirmed threshold without empirical multi-range temperature measurements.
  - ZenOmen's validated Windows restoration sequence must be strictly preserved:
    1. Disable Max Fan via `0x27 = 0`.
    2. Arm fan-control window via `0x10`.
    3. Reapply active thermal profile via `0x1A`.
    4. Never issue `0x2E {0,0}` on 8A3D/F.22.
  - Linux documentation must clearly distinguish kernel-level `hp-wmi` behavior from ZenOmen's userland Windows restoration path.
- **Root Cause:**
  - Embedded Controller firmware bug on board 8A3D when receiving opcode `0x2E {0,0}`; conflation of passive cooling curves with firmware lockups in early diagnostic notes.
- **Proposed Correction:**
  - Author authoritative hardware reference `docs/hardware/AUTO_FAN_VALIDATION.md` detailing the exact 8A3D/F.22 behavior, the safe restoration protocol, the distinction between passive 0 RPM and EC freeze, and a repeatable thermal load verification runbook.
  - Maintain the existing fail-closed safety check in `src/service/windows/victus_s.rs`.
- **Regression Test Required:**
  - Unit tests in `tests/fan_control_tests.rs` verifying state machine transitions.
- **Physical Hardware Validation Necessary:** **Yes.** Tested and verified on physical HP Victus 15-fb0xxx (8A3D / F.22).

### Issue AUD-02 (Release Artifacts / Legal Compliance): WiX v5 Open Source Maintenance Fee (OSMF) EULA CI Blocker
- **Criterion:** 7. Broken release artifacts / 8. Missing installer components
- **Severity:** **P1**
- **Exact File & Location:**
  - `.github/workflows/release.yml` (line 163)
  - `packaging/windows/ZenOmen.wxs` (duplicate file)
- **Current Behaviour:**
  - CI workflow attempted to install WiX Toolset via `dotnet tool install --global wix --version 5.0.2`.
  - WiX v5 requires explicit agreement to the .NET Foundation / FireGiant Open Source Maintenance Fee (OSMF) licensing terms, failing the CI build with error: `WIX7015: You must accept the Open Source Maintenance Fee (OSMF) EULA`.
  - Adding `-acceptEula` blindly would violate licensing compliance guidelines.
  - In addition, a duplicate file `packaging/windows/ZenOmen.wxs` existed alongside canonical `packaging/windows/wix/ZenOmen.wxs`.
- **Expected Behaviour:**
  - WiX MSI packaging must build deterministically without unreviewed legal acceptance flags.
  - WiX v4.0.6 (licensed under Microsoft Reciprocal License / MS-RL) is fully compatible with our WiX v4 syntax and does not require commercial OSMF EULA acceptance.
  - Duplicate `packaging/windows/ZenOmen.wxs` must be deleted, consolidating on `packaging/windows/wix/ZenOmen.wxs`.
- **Root Cause:**
  - Upgrading to WiX v5 introduced non-standard toolset EULA gates for automated CI environments.
- **Proposed Correction:**
  - Pin WiX toolset to `4.0.6` in `.github/workflows/release.yml`.
  - Delete duplicate `packaging/windows/ZenOmen.wxs` and point `wix build` command to `packaging/windows/wix/ZenOmen.wxs`.
- **Regression Test Required:**
  - Automated CI Windows build step executing `wix build packaging/windows/wix/ZenOmen.wxs -o dist/ZenOmen-x64.msi`.
- **Physical Hardware Validation Necessary:** No (toolchain & CI validation).

### Issue AUD-03 (Installation / Desktop Integration): Linux Mint AppImage Double-Click & FUSE 2/3 Compatibility
- **Criterion:** 4. Installation and uninstallation problems / 5. Missing dependencies
- **Severity:** **P1**
- **Exact File & Location:**
  - `packaging/linux/build-appimage.sh`
  - `packaging/linux/AppRun`
  - `docs/installation/LINUX_INSTALLATION.md`
- **Current Behaviour:**
  - Users downloading `ZenOmen-1.0.0-x86_64.AppImage` on Linux Mint 21 and Linux Mint 22 cannot open the application via double-click from Nemo file manager.
  - Terminal invocation initially failed with `Permission denied` because browsers do not set executable bit `chmod +x`.
  - Running `./ZenOmen-1.0.0-x86_64.AppImage --appimage-extract-and-run` succeeded, indicating that the bundled binary runs, but host FUSE 2 userspace mounting failed.
- **Expected Behaviour:**
  - Standard AppImage double-click should launch cleanly when host FUSE dependencies are present.
  - If launched without executable permissions or when FUSE is missing, clear installation guidance and fallback mechanisms (`--appimage-extract-and-run`) must be documented.
  - `AppRun` must include defensive runtime environment checks and diagnostic output if launched from terminal.
- **Root Cause:**
  - Linux Mint 21 (Ubuntu 22.04 base) and Linux Mint 22 (Ubuntu 24.04 base) do not ship with `libfuse2` by default. Mint 22 ships FUSE 3 (`libfuse3-3`), whereas standard Type-2 AppImages require `libfuse2` or `libfuse2t64` for FUSE mounting.
- **Proposed Correction:**
  - Add execution validation and clear diagnostic errors to `packaging/linux/AppRun`.
  - Author comprehensive installation guide `docs/installation/LINUX_INSTALLATION.md` documenting:
    - Mint 21: `sudo apt install libfuse2`
    - Mint 22: `sudo apt install libfuse2t64`
    - Permission setup: `chmod +x ZenOmen-1.0.0-x86_64.AppImage`
    - Extraction fallback: `./ZenOmen-1.0.0-x86_64.AppImage --appimage-extract-and-run`
- **Regression Test Required:**
  - Verification of `AppRun` syntax and execution via mock AppDir.
- **Physical Hardware Validation Necessary:** Yes (verified on Linux Mint / Ubuntu host).

### Issue AUD-04 (Installation Lifecycle / Permissions): Debian Package Service Lifecycle & D-Bus Reload
- **Criterion:** 4. Installation and uninstallation problems / 6. Incorrect permissions
- **Severity:** **P1**
- **Exact File & Location:**
  - `Cargo.toml` (`[package.metadata.packager.deb]`)
  - `packaging/linux/debian/postinst`
  - `packaging/linux/debian/prerm`
  - `packaging/linux/debian/postrm`
- **Current Behaviour:**
  - The Debian package installs `/usr/bin/zenomen`, `/usr/bin/zenomen-hw`, desktop entries, systemd unit, D-Bus system bus configs, and polkit policies.
  - However, maintainer scripts must ensure `systemctl daemon-reload`, `systemctl reload dbus`, `systemctl enable zenomen-hw.service`, and desktop/icon cache updates execute reliably without failing in containerized or non-systemd environments.
- **Expected Behaviour:**
  - Fresh `.deb` installation enables and starts `zenomen-hw.service`, configures D-Bus permissions, and updates desktop/icon caches.
  - Uninstallation cleanly stops and disables `zenomen-hw.service` without removing user settings in `$HOME/.config/zenomen`.
- **Root Cause:**
  - Debian packages that install system daemons and D-Bus system policies require maintainer scripts that defensively test for `/run/systemd/system` before invoking systemctl.
- **Proposed Correction:**
  - Maintainer scripts in `packaging/linux/debian/` now verify systemd presence before invoking service controls.
  - Document Debian installation procedure in `docs/installation/LINUX_INSTALLATION.md`.
- **Regression Test Required:**
  - Automated package inspection via `dpkg-deb -I` and `dpkg-deb -c`.
- **Physical Hardware Validation Necessary:** Yes (tested on Linux host).

### Issue AUD-05 (Hardware Safety & Capability Transparency): Motherboard Capability Registry
- **Criterion:** 3. Unsupported hardware assumptions / 11. Incorrect UI capability states
- **Severity:** **P1**
- **Exact File & Location:**
  - `src/hardware/registry.rs`
  - `src/service/windows/authorization.rs`
  - `src/hardware/windows/sensors.rs`
- **Current Behaviour:**
  - HP gaming laptops share WMI interfaces but differ drastically in EC register mappings, fan controllers, and RGB controllers.
  - Victus 15-fb0xxx (8A3D / F.22) supports CPU/GPU fan telemetry, Max Fan toggle, and display refresh switching, but lacks manual PWM fan curves and 4-zone RGB hardware.
  - Thermal profile writes via `0x1A` are accepted by the BIOS, but EC register readback is not available through userland ACPI methods.
- **Expected Behaviour:**
  - Hardware registry must fail-closed: unrecognized motherboards must have write controls disabled by default.
  - Manual PWM fan curves and RGB controls must remain labeled `Unsupported` on 8A3D.
  - Thermal profile state must remain labeled unverified where EC readback is absent.
  - Capabilities must never be artificially authorized just to make the UI look populated.
- **Root Cause:**
  - Vendor fragmentation across OMEN and Victus model lines.
- **Proposed Correction:**
  - Enforce explicit board capability table in `docs/hardware/AUTO_FAN_VALIDATION.md` and `src/service/windows/authorization.rs`.
- **Regression Test Required:**
  - Unit tests in `tests/sensor_registry_tests.rs`.
- **Physical Hardware Validation Necessary:** Yes (validated on 8A3D / F.22).

### Issue AUD-06 (Windows Packaging / Service Lifecycle): Windows Setup Wizard & SCM Lifecycle
- **Criterion:** 8. Missing installer components / 4. Installation and uninstallation problems
- **Severity:** **P1**
- **Exact File & Location:**
  - `packaging/windows/inno/ZenOmen.iss`
  - `packaging/windows/build-installer.ps1`
  - `packaging/windows/wix/ZenOmen.wxs`
- **Current Behaviour:**
  - Dual installer options exist (Inno Setup EXE and WiX MSI).
  - Inno Setup script manages SCM registration (`zenomen-hw.exe --install-service` / `--uninstall-service`), desktop shortcut, PATH integration, and autostart registry key.
  - WiX script manages native MSI service installation via `ServiceInstall` and `ServiceControl`.
- **Expected Behaviour:**
  - Windows installers must request administrative elevation only during installation, register `ZenOmenHardwareService` with delayed autostart, and preserve user configuration in `%APPDATA%\ZenOmen` during uninstallation or upgrades.
- **Root Cause:**
  - Privileged hardware service requires SCM registration and elevation, while the GUI application runs unprivileged under standard user token.
- **Proposed Correction:**
  - Author `docs/installation/WINDOWS_INSTALLATION.md` detailing both Inno Setup EXE and WiX MSI procedures, silent arguments (`/VERYSILENT`, `msiexec /qn`), and uninstallation verification.
- **Regression Test Required:**
  - CI build verifying Inno Setup compilation and WiX v4 MSI compilation.
- **Physical Hardware Validation Necessary:** Yes (Windows x64 SCM validation).

### Issue AUD-07 (Visual Quality & Asset Integrity): Authoritative Vector Asset Pipeline
- **Criterion:** 7. Broken release artifacts
- **Severity:** **P2**
- **Exact File & Location:**
  - `data/icons/zenomen.svg` (1024×1024 canonical master)
  - `scripts/branding/generate-branding.py`
  - `scripts/validate-icons.py`
  - `ui/app.slint` & `ui/components/sidebar.slint`
- **Current Behaviour:**
  - Earlier builds suffered from blurred icons due to downsampling raster PNGs into smaller PNGs and multi-res ICO files.
  - Slint UI components previously referenced raster PNGs instead of scalable vector assets.
- **Expected Behaviour:**
  - The canonical 1024×1024 SVG master (`data/icons/zenomen.svg`) must remain untouched and authoritative.
  - All raster icons (16, 24, 32, 48, 64, 128, 256, 512px) and the Windows ICO file (embedding 16, 24, 32, 48, 64, 128, 256px layers) must be rendered directly from the vector master.
  - Slint UI components render the SVG directly.
- **Root Cause:**
  - Chained bitmap downsampling in legacy shell scripts.
- **Proposed Correction:**
  - Python asset generator `scripts/branding/generate-branding.py` renders all targets directly from SVG without lossy compression.
  - Icon validation script `scripts/validate-icons.py` verifies integrity in CI and local verification.
- **Regression Test Required:**
  - `./scripts/validate-icons.py` passes with zero errors.
- **Physical Hardware Validation Necessary:** No (visual and asset validation).

### Issue AUD-08 (CI/CD Pipeline): Platform Artifact Separation & Release Determinism
- **Criterion:** 7. Broken release artifacts / 9. Unnecessary dependencies
- **Severity:** **P2**
- **Exact File & Location:**
  - `.github/workflows/ci.yml`
  - `.github/workflows/release.yml`
- **Current Behaviour:**
  - Linux and Windows builds run in separate GitHub Actions runners, but release packaging had mixed dependencies and potential toolchain conflicts.
- **Expected Behaviour:**
  - Strict platform artifact separation:
    - Linux builds produce ONLY: `zenomen_<version>_amd64.deb` and `ZenOmen-<version>-x86_64.AppImage`.
    - Windows builds produce ONLY: `ZenOmen-Setup-x64.exe`, `ZenOmen-x64.msi`, and `ZenOmen-windows-x64.zip`.
  - Zero cross-contamination: no Windows PE binaries in Linux archives; no Linux systemd units in Windows installers.
  - SHA-256 checksums generated and published per-platform (`SHA256SUMS-linux.txt`, `SHA256SUMS-windows.txt`).
- **Root Cause:**
  - Single-stage monolithic release scripts.
- **Proposed Correction:**
  - Updated `.github/workflows/release.yml` with isolated `release-linux` and `release-windows` jobs, publishing unified release on tag push.
- **Regression Test Required:**
  - CI workflow syntax validation and test execution.
- **Physical Hardware Validation Necessary:** No (CI infrastructure).

### Issue AUD-09 (Cross-Platform Isolation): Platform-Specific Dependencies & Modular Isolation
- **Criterion:** 2. Platform-specific compilation problems / 9. Unnecessary dependencies / 10. Duplicated hardware logic
- **Severity:** **P2**
- **Exact File & Location:**
  - `Cargo.toml`
  - `src/desktop/mod.rs`
  - `src/hardware/mod.rs`
  - `src/service/mod.rs`
- **Current Behaviour:**
  - Linux D-Bus library (`zbus`) was previously placed in general dependencies, causing Windows builds to link Unix types unnecessarily.
- **Expected Behaviour:**
  - Linux dependencies (`zbus`, `uzers`) restricted to `[target.'cfg(target_os = "linux")'.dependencies]`.
  - Windows dependencies (`windows-sys`, `winres`) restricted to `[target.'cfg(windows)'.dependencies]`.
  - Clean modular abstraction with shared data models in `src/service/types.rs`.
- **Root Cause:**
  - Unscoped dependency declarations in early development phases.
- **Proposed Correction:**
  - Conditional compilation strictly enforced across `Cargo.toml` and platform submodules.
- **Regression Test Required:**
  - `cargo check --target x86_64-unknown-linux-gnu` and `cargo check --target x86_64-pc-windows-msvc`.
- **Physical Hardware Validation Necessary:** No (compilation check).

### Issue AUD-10 (Runtime Telemetry): Dual-Process Process Memory Telemetry Accuracy
- **Criterion:** 1. Runtime bugs / 12. Missing diagnostics and error reporting
- **Severity:** **P2**
- **Exact File & Location:**
  - `src/hardware/process_memory.rs`
  - `src/hardware/linux/process_memory.rs`
  - `src/hardware/windows/process_memory.rs`
- **Current Behaviour:**
  - ZenOmen tracks memory for both GUI and `zenomen-hw` service.
  - If service is disconnected or measurement timestamps drift >10 seconds, reporting must not fabricate 0 MB or sum stale figures.
- **Expected Behaviour:**
  - Separate reporting of GUI Working Set, Private Bytes, Peak Working Set, and Hardware Service counterparts.
  - When service is offline, service metrics and combined metrics display "Unavailable" instead of 0 MB.
- **Root Cause:**
  - Dual-process architecture requires decoupled IPC telemetry with freshness guarantees.
- **Proposed Correction:**
  - Implemented `ZenomenMemoryTelemetry::new` in `src/hardware/process_memory.rs` with 10-second freshness gate and explicit availability flags.
- **Regression Test Required:**
  - Unit tests in `src/hardware/process_memory.rs`.
- **Physical Hardware Validation Necessary:** Yes (tested on live processes).
