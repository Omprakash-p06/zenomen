# Plan 05-03: Rebrand, Update Link & Removal of the Python CLI

## Objective

Present ZenOmen as its own project: a README that describes what ships today, an explicit
"Check for updates" action that opens the Releases page without downloading anything, a
NOTICE that keeps GPL-3.0, upstream attribution and the HP disclaimer intact, and removal
of the legacy Python CLI once — and only once — parity is documented as evidence.

## Context & Design Rules

- `README.md` today is still the upstream OpenOMEN page: title, badges pointing at
  `openomen/openomen`, a Discord invite, website and wiki links, and a feature list for the
  Python CLI. It must be rewritten, not patched.
- The HP disclaimer paragraph (`README.md`, `## Disclaimer`) and the GPL-3.0 notice are
  obligations, not content. Quoting them is not enough — they must remain present and
  unaltered in substance.
- **Not every `openomen` string may be deleted.** `src/rgb/mod.rs`, `src/rgb/migration.rs`,
  `src/main.rs`, `tests/rgb_tests.rs` and `ui/screens/lighting.slint` reference
  `~/.config/openomen/rgb` because that is where existing users' profiles live. That path
  is user data, not branding (RGB-05). A sweep that removes those breaks a shipped feature.
- REL-06 is the deliberate opposite of the upstream self-updater: open a page, never
  download, never execute. No network code is added to the application.
- REL-08 is gated on "once Rust parity is verified". The gate is a written evidence
  table, not an assertion in a commit message.
- Removal is a git-tracked deletion; it is reversible from history, but it must not happen
  in the same commit as an unverified behavioural change.

  <action>
    The tracer slice is the complete user path, wired before anything is widened.
    1. Create `src/desktop/releases.rs`:
       - `pub const RELEASES_URL: &str = "https://github.com/Omprakash-p06/zenomen/releases/latest";`
       - `pub fn open_releases_page() -> Result<(), ReleasesError>` that runs
         `std::process::Command::new("xdg-open").arg(RELEASES_URL).stdin(Stdio::null())
         .stdout(Stdio::null()).stderr(Stdio::null()).spawn()` and **does not wait** on the
         child. Never use a shell; never build the command from a variable.
       - `ReleasesError::Spawn(io::Error)` mapped to a short user-facing string.
       - No HTTP client, no download code, no version parsing — opening the page is the
         whole feature (REL-06).
    2. Declare the module in `src/desktop/mod.rs`.
    3. In `src/app.rs`, add a callback next to the existing ones in `install_callbacks`
       (lines 84-215):
       ```rust
       ui.on_open_releases_page(move || {
           if let Err(e) = crate::desktop::releases::open_releases_page() {
               tracing::warn!(error = %e, "could not open the releases page");
           }
       });
       ```
       Failure is a log line, never a panic and never a modal error — release builds use
       `panic = "abort"`.
    4. In `ui/screens/settings.slint`, add `callback open-releases-page();` to the component
       and a button inside the existing About block (around line 470) labelled
       "Check for updates", below the app-version row, using the existing button component
       and spacing tokens.
    5. Extend `tests/desktop_integration_tests.rs`:
       - `RELEASES_URL` starts with `https://`, ends with `/releases/latest`, and contains
         no `/releases/download/` segment (i.e. it can never point at an artifact).
       - `open_releases_page()` with `PATH` set to an empty directory returns `Err` rather
         than panicking, so the graceful-degradation path is covered.
    6. Verify manually once: click the action, confirm the browser opens the releases page
       and that no file is written to disk and no child process persists after the browser
       hands off.
  </action>

<threat_model>
| Threat ID | Component | Vulnerability / Attack Surface | Impact | Mitigation Strategy |
|---|---|---|---|---|
| T-05-09 | "Check for updates" action | A URL that could be redirected to an artifact, or a shell invocation built from a variable | Drive-by download or command injection from a UI click | The URL is a compile-time `https://` constant with no artifact path segment; the process is spawned with `Command::new` and literal arguments, never a shell string; the child is not waited on and no bytes are fetched. |
| T-05-10 | Removal of the Python CLI | Deleting the migration code paths with the branding sweep | Existing users lose their RGB profiles silently | The sweep distinguishes user-data paths from branding and Task 5 asserts `grep` returns only migration references; `tests/rgb_tests.rs` migration coverage must still pass. |
| T-05-11 | README install instructions | An install step that omits checksum verification or tells users to run an unverified download as root | Users install a tampered binary or escalate blindly | The README requires `sha256sum -c SHA256SUMS` before install and routes privileged system integration through the audited `--install-system-integration` command rather than a copied one-liner. |
| T-05-12 | Licensing compliance | Rebranding that drops upstream attribution or the HP disclaimer | GPL-3.0 violation and trademark exposure | `NOTICE` carries the upstream project, URL and license statement; `LICENSE` is asserted unmodified; the README disclaimer is a release-blocking acceptance criterion. |
</threat_model>
