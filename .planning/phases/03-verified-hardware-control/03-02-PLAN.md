# Plan 03-02: Verified Fan Control — Mode Read/Write, Read-Back Verification & Cooling Screen

## Objective
Implement client-side hardware control for cooling fans in the unprivileged GUI: build the `HardwareServiceClient` connecting to `com.zenomen.Hardware1`, wire `AppCommand::SetFanMode` through worker and state, update `ui/screens/cooling.slint` with interactive Auto and Max mode selectors, display verified read-back values, and honestly report `VerificationFailed` or connection errors (**COOL-01**, **COOL-02**, **COOL-03**, **COOL-04**, **COOL-05**, **COOL-06**, **SVC-06**).

## Context & Design Rules
- Follow [`03-RESEARCH.md`](file:///home/omprakash/Documents/zenomen/.planning/phases/03-verified-hardware-control/03-RESEARCH.md) specifications for fan control:
  - **Read-Only Telemetry Unprivileged (COOL-01, COOL-06):**
    - Per-fan RPM readings continue to be sampled unprivileged via `SensorRegistry` and `LinuxHardwareProvider`.
    - No polkit prompts or root permissions required to monitor fan speeds or view fan modes.
  - **Current Fan Mode & Validated Options (COOL-02, COOL-03):**
    - Show current mode (`Auto`, `Max`, `Manual`, or `Unknown(val)`).
    - Expose interactive controls strictly for `Auto` (`pwm1_enable = 2`) and `Max` (`pwm1_enable = 0`).
    - Manual mode (`1`) is displayed if the kernel reports it, but is **not** offered as a target choice in v1 because custom curve editing is deferred to v2.
  - **Verified Read-Back & Honest Error Reporting (COOL-04):**
    - Mode change triggers `SetFanMode` via `HardwareServiceClient`.
    - The UI updates to reflect the read-back state confirmed by hardware, NOT an optimistic local assumption.
    - If the write fails or fails read-back verification after retries, display the error (`VerificationFailed` or `AccessDenied`) in a clear notification banner with an explanation.
  - **Capability Gating & Graceful Degradation (COOL-05, SVC-06):**
    - If `has_fan_control` is false, hide/disable the buttons with a clear message: `"Fan control is not available on this machine (no writable pwm1_enable interface detected)"`.
    - If the hardware service is disconnected or stopped, disable the buttons with notice: `"Hardware service is disconnected — fan controls are disabled. Telemetry continues updating."`

## Tasks

### Task 1: D-Bus Client Layer (`HardwareServiceClient`)
- In `src/service/client.rs`:
  - Implement `HardwareServiceClient` managing connection to `com.zenomen.Hardware1` on system bus.
  - Define `ServiceConnectionStatus`: `Connected`, `Disconnected`, `Unavailable(String)`.
  - Implement `status(&self) -> ServiceConnectionStatus`.
  - Implement `get_fan_status(&self) -> Result<(String, Vec<u32>), String>`.
  - Implement `set_fan_mode(&self, mode: &str) -> Result<String, String>`.
  - Ensure client operations timeout gracefully and never block the UI thread or crash when the daemon is offline.
- Export `HardwareServiceClient` in `src/service/mod.rs`.

### Task 2: Core Events, State & Worker Integration
- In `src/core/events.rs`:
  - Add `AppCommand::SetFanMode(String)`.
  - Add `AppEvent::FanModeChanged(Result<String, String>)`.
  - Add `AppEvent::ServiceStatusChanged(ServiceConnectionStatus)`.
- In `src/core/state.rs`:
  - Add fields to `AppState`:
    - `fan_mode: String` (current verified mode)
    - `pending_fan_mode: Option<String>` (optimistic or inflight mode)
    - `service_status: ServiceConnectionStatus`
    - `last_control_error: Option<String>`
- In `src/core/worker.rs`:
  - Instantiate `HardwareServiceClient`.
  - In event loop, handle `AppCommand::SetFanMode`: invoke client, handle result, dispatch `AppEvent::FanModeChanged`.
  - Periodically check or verify service connection status.

### Task 3: Cooling Screen Slint UI Updates
- In `ui/screens/cooling.slint`:
  - Add properties:
    - `in property <bool> service-connected: true;`
    - `in property <string> active-fan-mode: "auto";`
    - `in property <string> pending-fan-mode: "";`
    - `in property <string> control-error-message: "";`
    - `callback set-fan-mode(string);`
    - `callback dismiss-error();`
  - Render Fan Mode Control Card:
    - Auto button (`"Auto"`) and Max button (`"Max"`).
    - Highlighting indicating current verified mode.
    - Spinner or pending indicator when `pending-fan-mode != ""` is inflight.
    - Disable buttons when `!root.has-fan-control || !root.service-connected`.
    - Capability notice / explanation banner when disabled.
    - Error banner displaying `control-error-message` if verification fails.
- In `ui/app.slint`:
  - Wire cooling screen properties to `AppWindow` properties.
  - Wire `set-fan-mode` callback to Rust application bridge.

### Task 4: Slint Application Bridge & Integration Testing
- In `src/app.rs`:
  - Bridge `set-fan-mode` callback from Slint window to `AppCommand::SetFanMode`.
  - Bridge `AppState` updates (`fan_mode`, `service_status`, `last_control_error`) to Slint UI properties.
- In `tests/fan_control_tests.rs`:
  - Unit tests verifying `SetFanMode` command dispatch, state updates on success, and state updates on `VerificationFailed` error.
  - Test UI state property mapping for absent fan control vs service disconnected.
