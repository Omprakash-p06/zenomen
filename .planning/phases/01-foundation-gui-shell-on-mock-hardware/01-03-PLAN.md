# Plan 01-03: Mock Provider, Monitoring Worker, Bounded History Charts & Benchmark Instrumentation

## Objective
Deliver a runnable, end-to-end ZenOmen application driven entirely by a configurable mock hardware provider (**FOUND-03**), with a non-blocking background monitoring worker (**PERF-03**), rolling telemetry charts backed by a bounded 120-sample history ring buffer (**MON-09**), multi-series SVG chart rendering, and empirical memory/frame-time benchmarking instrumentation.

## Context & Design Rules
- Follow [`01-UI-SPEC.md`](file:///home/omprakash/Documents/zenomen/.planning/phases/01-foundation-gui-shell-on-mock-hardware/01-UI-SPEC.md):
  - `Sparkline`: 28px height, 2px stroke `Path` with no axes or labels.
  - `TelemetryChart`: 160px height plot, 3 horizontal grid lines at 1px Outline (`#262A33`), 3 series paths:
    - CPU utilization: Gold `#C6A15B`
    - GPU utilization: Text Secondary `#9BA1AC`
    - RAM usage: Neutral Tint `#5D6470`
  - Fewer than 2 samples renders "Waiting for first reading" text instead of a flat 0 line.
  - Sensor data gaps (`None` samples) render as path breaks (`M` commands) rather than connecting across gaps.
- Strictly bounded memory (**PERF-04** preparation):
  - `VecDeque<TelemetryPoint>` capped at 120 entries; `pop_front()` before `push_back()`.
  - Update Slint model properties in place rather than rebuilding arrays on every tick.
- Non-blocking execution (**PERF-03**):
  - Monitoring worker runs in a separate `std::thread`, scheduled on deadlines.
  - Handles `AppCommand::RefreshTelemetry` via `recv_timeout(deadline - now)` for immediate response without sleep latency.
- Headless CI execution:
  - Unit and integration tests in `tests/benchmark_tests.rs` execute cleanly in headless environments without requiring a live display server.

    Addresses review concern: Worker Thread Responsiveness to On-Demand Refresh (01-REVIEWS.md:57).

    1. Create `src/core/worker.rs`:
       - Function `pub fn spawn_monitoring_worker(provider: Arc<dyn HardwareProvider>, event_sender: mpsc::Sender<AppEvent>, command_receiver: mpsc::Receiver<AppCommand>) -> thread::JoinHandle<()>`:
         - Initializes `TelemetryHistory::new()`.
         - Dispatches initial `AppEvent::CapabilitiesLoaded(provider.capabilities())`.
         - Loop with deadline tracking:
           - Computes target deadline: `let mut deadline = Instant::now() + Duration::from_secs(1);`
           - Waits for commands using `command_receiver.recv_timeout(deadline.saturating_duration_since(Instant::now()))`.
           - If `AppCommand::RefreshTelemetry` is received: immediately samples without waiting, and resets `deadline = Instant::now() + Duration::from_secs(1)`.
           - If `AppCommand::Navigate(_)` or other commands: processes as appropriate.
           - On timeout (deadline reached):
             - Samples `provider.sample_telemetry()`.
             - Records telemetry point into `TelemetryHistory`.
             - Generates SVG paths for CPU, GPU, and RAM.
             - Sends `AppEvent::TelemetryUpdated(snapshot)` to main thread.
             - Schedules Slint property updates inside `slint::invoke_from_event_loop`.
             - Advances deadline by 1 second.
       - Guarantees `PERF-03`: sampling never sleeps inline or blocks UI thread callbacks.
    2. Update `src/main.rs` to wire the worker thread to `ZenOmenApp`.
  </action>
  <acceptance_criteria>
    - Worker thread uses `recv_timeout` on command receiver, handling on-demand refresh without sleeping.
    - Worker periodically samples and dispatches `AppEvent::TelemetryUpdated`.
    - Main thread remains completely unblocked by worker execution.
